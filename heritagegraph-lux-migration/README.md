# HeritageGraph ↔ LUX migration

Ontology alignment and migration pipeline that lifts Yale's [LUX](https://lux.collections.yale.edu/) (Linked Art / CIDOC-CRM) cultural-heritage records into the [CAIR Nepal HeritageGraph](https://github.com/CAIRNepal/heritagegraphontology) knowledge graph.

| | |
|---|---|
| Source dataset | LUX — more than 41 million Linked Art records across objects, persons, places, concepts, events, sets, works ([Sanderson 2024](https://doi.org/10.16995/olh.15407)) |
| Target dataset | HeritageGraph — Nepal-focused cultural heritage ontology |
| Alignment | 772 OWL triples (59 module classes, 3 of them deprecated, and 34 object properties; 0 `owl:equivalentClass`, 167 `rdfs:subClassOf`, 1 `owl:equivalentProperty`, 44 `rdfs:subPropertyOf`, 14 SKOS mappings) |
| Version | 1.1.0 (versionIRI `https://cair-nepal.org/heritagegraph/alignment/lux/1.1.0`), follows HeritageGraph 1.1.0; terms the module mints are marked `rdfs:isDefinedBy` it, and the module passes the `lux-conservativity` gate |
| Migration tooling | Python (`rdflib`, `pyoxigraph`) + SPARQL CONSTRUCTs + Docker Compose |
| Target triplestore | [Oxigraph](https://github.com/oxigraph/oxigraph) — embedded or HTTP |
| Status | alignment verified · pilot ready · server-deployable |

## Quick start (local pilot — ~30 min)

```bash
git clone https://github.com/CAIRNepal/heritagegraph-lux-migration.git
cd heritagegraph-lux-migration

# 1. fetch HeritageGraph.ttl into alignment/
curl -L -o alignment/HeritageGraph.ttl \
  https://raw.githubusercontent.com/CAIRNepal/heritagegraphontology/main/ontology/HeritageGraph.ttl

# 2. configure
cp docker/.env.example docker/.env
$EDITOR docker/.env        # RING_MODE=crawl, LIMIT_PER_QUERY=10000 by default

# 3. run
make up
make logs                  # follow migration progress
make status                # triple counts per named graph
make validate              # V1/V2 hard-gate validation
```

## Quick start (server deployment)

Targets `server42.dnsbilisim.net` (or override via `.deploy.env`):

```bash
# first time only — provisions Docker, /root/github/heritagegraph-lux-migration/, systemd unit, logrotate
make deploy-bootstrap

# every deploy
make deploy                # rsync repo + docker compose up -d --build

# observe
make ssh-status
make ssh-logs-migrator
```

Full playbook: [`docs/DEPLOY_SERVER.md`](docs/DEPLOY_SERVER.md).

## What's inside

### The alignment (`alignment/heritagegraph-lux-alignment.ttl`)

* **68 class rows / 69 property rows** in the mapping workbook (including identity, deprecated and dropped rows), mapped to `crm:` (CIDOC-CRM) or `la:` (Linked Art-only — only seven of these exist; the rest of the LUX short names expand directly to `crm:` URIs).
* **15 CIDOC-CRM classes reused directly** (no `hg:` wrapper), as the core does: Person, HumanMadeObject, Actor, Place, TimeSpan, Material, Production, Destruction, TransferOfCustody, ConditionAssessment, ConditionState, Technique, and since 1.1.0 Group (`crm:E74_Group`), Death (`crm:E69_Death`) and generic Activity (`crm:E7_Activity`).
* **59 HG classes defined by this module** (`rdfs:isDefinedBy` the module) for full LUX migration coverage — e.g. Birth, Formation, Dissolution, Acquisition, Move, VisualItem, LinguisticObject, DigitalObject, Set, Identifier, Name, MeasurementUnit, Dimension, Right, LegalObject, Modification, Language, Currency, BeginningOfExistence, EndOfExistence, PropositionalObject, Measurement, Inscription, Title, CuratedHolding, CurationActivity, MonetaryAmount, AttributeAssignment, Period, Encounter, ProvenanceActivity, and the six genuine `la:` activity classes. Three of them (`hg:Group`, `hg:Death`, `hg:Activity`) are deprecated in 1.1.0 in favour of the CRM classes.
* Verified against the [official Linked Art JSON-LD context](https://linked.art/ns/v1/linked-art.json) — see [`docs/VERIFICATION_FINDINGS.md`](docs/VERIFICATION_FINDINGS.md) for the six material bugs found and fixed.

### The migration (`scripts/migrate_lux_to_hg.py`)

Four operational modes, each invokable from the CLI:

| Mode | What it does |
|---|---|
| `crawl` | REST-fetch records from LUX's `/api/search/*` endpoints, write JSON-LD to disk |
| `transform` | Batched SPARQL `INSERT WHERE` over the LUX raw graph → HG instances in the imported graph |
| `validate` | Runs the 8 validation queries; V1/V2 are hard gates (exit 1 on failure) |
| `delta` | Pull the latest LUX diff, apply it, re-run validation |

### The Docker stack (`docker/`)

Three services:

* **oxigraph** — Rust-based SPARQL 1.1 triplestore, persistent volume, healthcheck.
* **migrator** — one-shot container that runs the 7-phase pipeline (fetch → bulk-load → load HG → transform → validate → snapshot → master flag). Idempotent via flag files.
* **delta-syncer** — long-running container, supercronic-driven weekly delta sync after the initial migration completes.

## How LUX data gets in

LUX does **not** publish a public bulk dump as of May 2026. Realistic paths (detailed in [`docs/LUX_DATA_DOWNLOAD.md`](docs/LUX_DATA_DOWNLOAD.md)):

1. **Email Yale** ([lux@yale.edu](mailto:lux@yale.edu)) for an academic-use dump — recommended, ~1-2 weeks turnaround.
2. **IIIF Change Discovery / ActivityStreams** — Yale's blessed harvester protocol (~3-4 days for full dataset).
3. **REST per-record crawl** — `scripts/migrate_lux_to_hg.py --mode crawl`, ~2-4 days for full, ~30 min for a 10K-record pilot.
4. **LuxY Python wrapper** — Yale's official client at https://github.com/project-lux/luxy.
5. **Selective subset** — filter to South/East Asian religious heritage (~50-200K records, 6-12 hours) — recommended production scope.

Run `scripts/discover_lux_endpoints.sh` first to see which endpoints are actually responding before configuring `.env`.

## Validation gates

After migration, `make validate` runs eight queries (`queries/validation_queries.sparql`). Two are **hard gates**:

* **V1** — every LUX class type must have a HG target class. Returns 0 rows when alignment is complete.
* **V2** — every imported HG instance must carry exactly one `owl:sameAs` back to its LUX origin URI.

The other six (count parity, unaligned-property usage, round-trip spot-check, HG-native class preservation, unique type per record, orphan check) are informational.

## Results

### Pilot run — May 2026 (server42, Oxigraph 0.4.4)

> Produced by alignment **v0.1.0** (273 triples, `https://w3id.org/heritagegraph/` namespace), which predates HeritageGraph 1.0.0. The raw harvest and the store are not published, so these figures are a dated record, not a reproducible benchmark: they cannot be regenerated from this release. Details: [`docs/PILOT_RUN.md`](docs/PILOT_RUN.md).

| | |
|---|---|
| Harvest | keyword-selected: `RING_MODE=crawl`, `LUX_FILTER="religious heritage"`, `LIMIT_PER_QUERY=10000` |
| LUX records fetched | **20,871** (≈0.05 % of LUX's more than 41 million records) |
| Raw LUX graph | **3,467,368** triples |
| Typed nodes in raw graph | **898,656** across **28** CRM / CRMdig / CRMsci / Linked Art classes (counted 2026-06-23) |
| Imported HG graph | **98,131** triples, **32,342** instances in five classes, each `owl:sameAs` its LUX origin |

| HG class (1.1.0 name) | Migrated | Raw LUX nodes of that class |
|---|---:|---:|
| `crm:E21_Person` (pilot: `hg:Person`) | 25,281 | 25,285 |
| `crm:E74_Group` (pilot: `hg:Group`) | 3,558 | 3,572 |
| `crm:E53_Place` (pilot: `hg:Place`) | 3,281 | 3,281 |
| `crm:E22_Human-Made_Object` (pilot: `hg:HumanMadeObject`) | 137 | 163 |
| `hg:Set` | 85 | 85 |
| **total** | **32,342** | **32,386** |

The 32,342 instances exceed the 20,871 records fetched because LUX records carry typed references to other entities (persons, places); they are entities, not records.

**Known gaps:** the activity, work and embedded-node templates produced no instances in this run, so 32,342 is 99.9 % of the nodes in the five handled classes but 3.6 % of all typed nodes. Templates added since (10 in total) cover these branches but have not been re-run on the server. V1 passed although whole branches were empty, because it checks classes, not instances.

### Coverage against HeritageGraph 1.1.0 (recomputed 2026-11-28)

All **28/28** LUX class types (898,656 nodes) have a HeritageGraph target. **13** of them (208,735 nodes, 23.2 %) are CIDOC-CRM classes that the HeritageGraph core uses: 9 (75,504 nodes) it reuses directly as its own classes, and 4 (`crm:E55_Type`, `crm:E13_Attribute_Assignment`, `crm:E4_Period`, `crm:E73_Information_Object`; 133,231 nodes) are superclasses of core classes. **15** (689,921 nodes, 76.8 %) are reached only through `hg:` subclasses that this alignment declares; the core alone covers none of them (the largest are `crm:E33_E41_Linguistic_Appellation`, 258,678; `crm:E33_Linguistic_Object`, 188,712; `crm:E65_Creation`, 136,441 — mostly embedded name, text and creation nodes). Coverage is structural: it shows that every LUX type has a place in the alignment, not that LUX instances become HeritageGraph instances. Reproduce it with `python3 evaluation/lux/generate_lux_eval.py --offline` in the HeritageGraph repository (output: `evaluation/lux/LUX_EVALUATION.md`).
